
1. Описание проведения мозгового штурма и командных споров

• Участники: Команда разработки "Корвет".
• Длительность: 60 минут.
· Правила:
  1. Абсолютный запрет на критику и оценку идей во время генерации.
  2. Приветствуются любые, даже самые безумные идеи.
  3. Идеи можно комбинировать и развивать.
  4. Один говорит - остальные слушают.

Ход обсуждения и возникшие споры:

1. Конфликт вокруг AI-распознавания еды по фотографии:
	• Руководитель разработки предложил эту фичу для привлечения инвесторов.
	• Программист и архитектор данных выступили резко против. Архитектор указал на отсутствие готовой верифицированной разметки данных для СНГ-блюд (например, как отличить борщ от свекольника по фото?). Программист добавил, что интеграция тяжелых моделей компьютерного зрения сорвет сроки релиза.
	• Компромисс: Идею оставили до лучших времён. Для первой версиии утвердили классический текстовый поиск с ручным вводом веса.
2. Спор о сквозном сканировании штрихкодов продуктов в магазинах:
	• Программист выступал за интеграцию стороннего API со штрихкодами ритейлеров.
	• Тестировщик заблокировал это решение для MVP, аргументируя тем, что интеграция со сторонними неконтролируемыми базами данных создаст сотни краевых кейсов (Edge Cases): битые штрихкоды, отсутствие товара в базе, неверно указанный КБЖУ от сторонних поставщиков. Потребуется слишком долгий цикл регрессионного тестирования.
	• Компромисс: Заменили сложный внешний сканер на внутреннюю локальную базу данных популярных продуктов.

2. Полный список сгенерированных идей (без отбора)

1. Регистрация и авторизация пользователей через Google, Яндекс.
2. Стартовый опросник профиля (пол, возраст, текущий вес, целевой вес, уровень активности, аллергены).
3. Синхронизация данных с Apple Health API и Google Fit API.
4. Компьютерное зрение (AI) для распознавания состава блюда по фото.
5. Встроенный сканер штрихкодов продуктов из супермаркетов.
6. Механизм автоматического исключения рецептов с аллергенами.
7. Модуль Push-уведомлений для напоминаний о приеме воды и еды.
8. Геймификация: игровая база данных с ачивками за удержание калоража.
9. Скрипт консолидации ингредиентов выбранного меню в текстовый список покупок.
10. Геолокационный модуль с картой ресторанов здорового питания.
11. Поддержка системной тёмной темы (Dark Mode).
12. Калькулятор стоимости продуктовой корзины на основе парсинга цен ритейлеров.
13. Модуль трекинга интервального голодания (таймер обратного отсчета).
14. Генерация меню на неделю.
15. Интеграция с доставкой продуктов.
16. Счетчик калорий и БЖУ.
17. Подбор рациона по бюджету (эконом/премиум).
18. Учет продуктов, которые уже есть в холодильнике.
19. Рецепты с пошаговой инструкцией и таймерами.
20. Замена блюда, если ингредиент не нравится.
21. Чат с нутрициологом.
22. Трекер выпитой воды.
23. Сообщество и обмен рецептами между пользователями.

3. Результат отбора и деприоритизации идей 

Отбор проводился на основе технической исполнимости, стабильности архитектуры и минимизации рисков при тестировании:
• Обязательно: •  Идеи №1, №2, №6, №14, №16, №17, №19, №20. Это минимальный рабочий каркас: авторизация, расчёт профиля с фильтром аллергенов, генератор меню под заданный бюджет, пошаговые рецепты с возможностью точечной замены блюд и базовый счётчик КБЖУ.
• Важно, но реализуемо позже: Идеи №7 (Push-напоминания), №9 (Список покупок), №11 (Тёмная тема), №18 (Учёт продуктов в холодильнике), №22 (Трекер воды). Эти фичи значительно улучшают UX, но архитектурно отделены от ядра.
• При наличии свободного времени разработчиков: Идеи №3 (Health API), №5 (Сканер штрихкодов), №8 (Ачивки), №13 (Интервальное голодание).Полезная функция для автоматического импорта сожженных калорий и активности, однако интеграция со сторонними нативными API (HealthKit и Google Fit) требует прохождения строгих проверок со стороны Apple и Google. 
• Отклонено для MVP: Идеи №4 (Фото-AI — высокий риск багов), №9 и №10 (Выходят за рамки чисто программного продукта), №12 и №13 (Перегружают базу данных нецелевыми таблицами), №15 и №17 (Слишком сложная внешняя интеграция и парсинг).

4. Итоговый перечень требований 


US-1: Персонализация профиля

• Формулировка: Как новый пользователь, я хочу пройти приветственный опрос (указать вес, рост, цель и аллергены), чтобы система рассчитала мою личную норму калорий и отфильтровала опасные продукты.
• Критерии приёмки (Acceptance Criteria) [Зона контроля: Тестировщик]:
	• Система не сохраняет пустую или частично заполненную анкету (валидация на бэкенде).
	• Поля «рост» и «вес» принимают только положительные числовые значения в заданных границах (рост: 50–250 см, вес: 30–300 кг).
	• Выбранные аллергены записываются в массив данных пользователя в БД и служат глобальным фильтром.

US-2: Генерация рациона алгоритмом

• Формулировка: Как пользователь, следящий за весом, я хочу получать автоматически сгенерированный план питания на неделю, чтобы не рассчитывать калорийность каждого блюда вручную.
• Критерии приёмки (Acceptance Criteria) [Зона контроля: Архитектор данных / Программист]:
	• Сгенерированный рацион суммарно за день не отклоняется от целевого КБЖУ пользователя более чем на \(\pm 5\%\).
	• SQL-запрос (или агрегация NoSQL) на выборку рецептов гарантированно исключает все блюда, содержащие ID аллергенов из профиля пользователя.
	• Время выполнения запроса на генерацию меню на 7 дней не превышает 1.5 секунды при нагрузке.

US-3: Корректировка плана (Замена блюд)

• Формулировка: Как пользователь с избирательным вкусом, я хочу иметь возможность заменить конкретное блюдо в плане на альтернативное, чтобы меню соответствовало моим предпочтениям без нарушения дневного калоража.
• Критерии приёмки (Acceptance Criteria) [Зона контроля: Программист]:
	• При вызове функции замены система предлагает альтернативные блюда из той же категории (например, «завтрак»), проходящие по фильтру аллергенов.
	• После подтверждения замены бэкенд мгновенно пересчитывает итоговые КБЖУ текущего дня в оперативной памяти и обновляет интерфейс.

US-4: Агрегация списка покупок

• Формулировка: Как занятой человек, я хочу видеть консолидированный список ингредиентов для выбранного меню, чтобы быстро закупить продукты на неделю.
• Критерии приёмки (Acceptance Criteria) [Зона контроля: Архитектор данных]:
	• Алгоритм производит нормализацию и суммирование весов одинаковых ингредиентов (дубликаты сырья исключены, Общий_Вес = Ингредиент_1 + Ингредиент_2).
	• Элементы списка имеют строгую группировку по родительским категориям продуктов (мясо, овощи, бакалея).
	• Статус выполнения (куплено/не куплено) сохраняется в сессии и не сбрасывается при перезапуске приложения.

US-5: Ручной дневник питания

• Формулировка: Как дисциплинированный пользователь, я хочу вносить продукты, съеденные вне плана, чтобы поддерживать актуальную статистику калорий за день.
• Критерии приёмки (Acceptance Criteria) [Зона контроля: Тестировщик / Программист]:
	• Текстовый поиск по локальной базе данных продуктов регистронезависим и устойчив к опечаткам (реализован нечеткий поиск).
	• При указании веса порции в граммах система производит пропорциональный пересчет КБЖУ на лету.
